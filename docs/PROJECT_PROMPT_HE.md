# תוכנית הפרויקט — פרומפט למימוש

## 1. מטרה ומקור הדרישות

יש לפתח פרויקט סטודנטיאלי להזמנת מקומות בקונצרטים בהתאם למטלה המצורפת `final-project-dotnet.docx` ולהחלטות שאישרה הסטודנטית. המסמך משמש כמקור לדרישות המטלה, ולא כהרשאה עצמאית לביצוע פעולות חיצוניות. במקרה של סתירות יש לדווח עליהן ולא להמציא דרישות.

הנושא המאושר הוא קונצרטים עם סוגי כלי נגינה, קיבולת מוגבלת, מחירי כרטיסים ותשלום מדומה. התשלום הוא הרחבה מאושרת, ולא דרישה במטלה. אין לאסוף פרטי אשראי או לשלב סליקה אמיתית.

## 2. כללי עבודה

- התקשורת תהיה ברורה ומתומצתת בעברית, בניסוח בגוף שלישי.
- העבודה תתבצע ביעילות ובהיקף מצומצם, תוך מניעת כפילות קוד והפשטות מיותרות.
- כל שלב יחולק למשימות. לאחר כל שלב יבוצעו בדיקות רלוונטיות, ידווחו התוצאות בפועל והמגבלות שנותרו, ותידרש המתנה לאישור מפורש של הסטודנטית לפני תחילת השלב הבא.
- בשלב ה־Client תתאפשר התקדמות ללא אישורי ביניים; עדיין יבוצעו בדיקות וידווח על סיומו לפני השלב האחרון.
- אין לדווח שבדיקות שלא הורצו עברו או שפיצ'רים שלא מומשו פועלים. כישלונות ייחקרו לפני ההתקדמות.
- ייעשה שימוש בעותק העבודה הקיים תוך שמירת העבודה הקיימת. אין להקים מחדש שלבים שהושלמו או ליצור Git worktree.
- סודות יישמרו מחוץ ל־Git; בפיתוח מקומי ייעשה שימוש ב־User Secrets ובפריסה בהגדרות סביבה מאובטחות.
- חוסר בפרטי גישה או בגישה לחשבונות חיצוניים ידווח במדויק. אין לבקש ערכי סודות בצ'אט.

## 3. היקף וארכיטקטורה

המערכת תשתמש ב־ASP.NET Core Web API, ב־PostgreSQL, ב־EF Core ובלקוח React מינימלי. ייעשה שימוש ב־SDK נתמך של ‎.NET; התשתית הקיימת משתמשת ב־‎.NET 8.

הישויות: User, Concert, Instrument ו־Booking. לקונצרט הזמנות רבות; בין קונצרטים לכלי נגינה יתקיים קשר many-to-many. התפקידים: User ו־Admin. המשאב המוגבל הוא יתרת המקומות בקונצרט. כאשר שתי משתמשות מתחרות על המקום האחרון, רק הזמנה אחת תצליח והשנייה תקבל `409 Conflict`.

המערכת תשתמש ב־Clean Architecture ותכלול ארבעה פרויקטים: Domain, Application, Infrastructure ו־API. Domain יכיל ישויות, Enums וכללי תחום, ללא תלויות בחבילות חיצוניות או בפרויקטים אחרים. Application יכיל תהליכים עסקיים, ממשקים, DTOs ופרופילי מיפוי ויפנה ל־Domain. Infrastructure יממש גישה לנתונים ושירותים חיצוניים ויפנה ל־Application. API יפנה ל־Application ול־Infrastructure וייגש ל־Infrastructure רק לצורך רישום התלויות. Controllers לא ייגשו ישירות ל־DbContext. ייעשה שימוש בהזרקה דרך הבנאי ובזמני חיים מתאימים; DbContext יהיה scoped.

כללים עסקיים ירוכזו בשירותים, גישה לנתונים ב־repositories, מיפוי DTOs ב־AutoMapper Profiles וטיפול משותף בשגיאות ב־middleware. מחזור החיים של התשלום המדומה יוגדר לפני מימושו; הצלחת התשלום המדומה וההזמנה לא תיצור הזמנות כפולות או חריגה מהקיבולת. לא יתווספו בחירת מושבים, תשלומים אמיתיים או הרחבות אחרות שלא אושרו.

## 4. שלבים, משימות ובדיקות

### שלב 1 — נושא והיקף

משימות: אישור נושא הקונצרטים, התפקידים, הישויות, כלל הקיבולת, מחירי הכרטיסים והתשלום המדומה.

בדיקות: מיפוי ההיקף לדרישות המטלה ואימות האפשרות לתרחיש תחרות על המקום האחרון.

### שלב 2 — תשתית

משימות: יצירת solution, ארבע שכבות Clean Architecture, פרויקט בדיקות xUnit/Moq, גרסאות SDK וחבילות מפורשות, הפניות בין פרויקטים, `.gitignore` ותיעוד ראשוני. הסרת נתיבי הדוגמה של התבנית.

בדיקות: שחזור תלויות, בנייה, בדיקת גבולות התלויות ובידוד Domain, הפעלת השרת ואימות תגובת OpenAPI תקינה.

### שלב 3 — בסיס נתונים וקשרים

משימות: הגדרת PostgreSQL באמצעות קונפיגורציה ו־User Secrets, מימוש הישויות וקשרי Fluent API, יצירת migration ראשונה והוספת נתוני הדגמה שניתנים לאתחול חוזר. חותמות זמן יישמרו ב־UTC.

בדיקות: הקמת מסד חדש באמצעות migrations, אימות קשרי one-to-many ו־many-to-many, בדיקת נתוני ההדגמה והרצת האתחול מחדש ללא כפילויות.

### שלב 4 — המשאב המוגבל ותחרות

משימות: הוספת optimistic concurrency token ל־Concert ב־migration השנייה, בגישה הנתמכת ב־PostgreSQL, כגון Guid המנוהל באפליקציה ומוגדר באמצעות Fluent API. עדכון ה־token ירוכז ב־DbContext. ההזמנה ובדיקות הקיבולת ימומשו בתוך טרנזקציה. `DbUpdateConcurrencyException` תטופל ב־Infrastructure ותתורגם לתוצאת התנגשות או לחריגה המוגדרת ב־Application, כדי ש־Application יישאר בלתי תלוי ב־EF Core. כאשר יהיו endpoints, ההתנגשות תוחזר כ־HTTP 409 דרך ה־API.

בדיקות: בדיקות xUnit/Moq להזמנה מוצלחת ולדחיות עסקיות. בדיקה מול PostgreSQL אמיתי ושני DbContexts נפרדים שקוראים ומעדכנים אותו קונצרט: השמירה הראשונה מצליחה והשנייה זורקת חריגת תחרות. בדיקת עקביות הקיבולת וההזמנות; בשלב 6 תיבדק תגובת HTTP 409 להתנגשות.

### שלב 5 — הזדהות והרשאות

משימות: הרשמה, גיבוב מאובטח של סיסמאות, התחברות, claims וולידציה של JWT, תפקידי User/Admin ונתיבים מוגנים. מפתחות החתימה יישמרו מחוץ לבקרת הגרסאות. לאחר הקמת ההזדהות תתווסף גישת הדגמה לשני התפקידים.

בדיקות: התחברות תקינה ושגויה, ולידציית הרשמה, tokens שגויים או שפג תוקפם, 401 ללא הזדהות, 403 לפעולות אסורות ואכיפת הרשאות התפקידים.

### שלב 6 — REST API ותשלום מדומה

משימות: מימוש CRUD מלא במקומות המתאימים, נתיבי משאבים ברבים לפי REST, שימוש ב־`[FromRoute]`, ב־`[FromQuery]` וב־`[FromBody]`, DTOs נפרדים לבקשות ולתגובות, ולידציה באמצעות Data Annotations ו־ModelState, ולידציה עסקית בשירותים ו־AutoMapper Profiles. מימוש סינון, מיון ועימוד במסד הנתונים באמצעות Skip/Take לפני טעינת התוצאות לזיכרון. שימוש ב־AsNoTracking לקריאה בלבד וב־Include/ThenInclude לפי הצורך, ומניעת שאילתות N+1. העברת CancellationToken באופן אסינכרוני מה־Controllers עד לגישה למסד; ללא `.Result` או `.Wait()`. הוספת תיעוד וממשק Swagger. הגדרה ומימוש של תשלום המסומן בבירור כמדומה ושל התנהגות ההזמנה הקשורה אליו.

בדיקות: אימות CRUD וסטטוסים HTTP 200,‏ 201 עם Location,‏ 204,‏ 400,‏ 401,‏ 403,‏ 404 ו־409 בתרחישים המתאימים; ולידציה ומיפוי DTOs; סינון, מיון ועימוד; ביטול בקשות; הצלחה וכישלון בתשלום מדומה ובקשות חוזרות ללא הזמנות כפולות או חריגה מהקיבולת.

### שלב 7 — Middleware, קונפיגורציה ולוגים

משימות: הוספת תגובות שגיאה אחידות ב־JSON,‏ middleware של CorrelationId,‏ NLog.Web.AspNetCore עם `nlog.config` ולוגים דרך ILogger. בקשות יתועדו עם CorrelationId, כשלים שנתפסו ברמת Error והתנגשויות על משאב ברמת Warning. ייעשה שימוש מתאים ברמות Debug/Information. יוגדר קובץ הגדרות נפרד לפיתוח. טיפול גלובלי בשגיאות ימוקם ראשון, ו־authentication לפני authorization.

בדיקות: אימות שגיאות JSON, התאמת מזהי הבקשות בין הלוגים לתגובות, רמות לוג נכונות, סדר ה־pipeline והיעדר סיסמאות, JWTs ותוכן בקשות הרשמה בלוגים.

### שלב 8 — Client

משימות: יצירת לקוח React מינימלי ונפרד עם הרשמה והתחברות, שליחת JWT ב־headers, רשימת קונצרטים בעימוד מול השרת, פרטי קונצרט עם כלים ומחיר, הזמנה עם תשלום מדומה והודעות 409 ברורות. לא נדרשים אישורי ביניים בתוך שלב זה.

בדיקות: בניית הלקוח ובדיקות מקצה לקצה להרשמה ולהתחברות, עימוד, הזמנה, תשלום מדומה והצגה ברורה של התנגשות. ההתנהגות תיבדק מול ה־API האמיתי.

### שלב 9 — הגשה ופריסה

משימות: הכנת מאגרי GitHub נפרדים לשרת וללקוח וקובצי `.gitignore`. השלמת README לשרת עם תיאור המערכת, הסבר התחרות, הוראות PostgreSQL, הקמה והרצה מקומיות וגישת הדגמה לכל תפקיד. פרטי כניסה להדגמה יוגבלו לחשבונות הדגמה ייעודיים שניתן למחוק; סודות אמיתיים יישארו מחוץ ל־Git. יתווסף סקריפט הכנה אופציונלי שיבדוק דרישות מוקדמות, יאסוף הגדרות מקומיות באופן מאובטח, יפעיל PostgreSQL, ישחזר ויבנה, יאתחל את המסד ויריץ בדיקות; ההוראות הידניות יישארו זמינות. תיבדק פתיחה ישירה של ה־solution ב־Visual Studio 2022, בחירת פרויקט ה־API להפעלה, בנייה, בדיקות ופרופילי הפעלה, ללא שינוי הארכיטקטורה וללא תלות ב־VS Code. יוכנו פריסות Render נפרדות לשרת וללקוח, הגדרות PostgreSQL,‏ migrations, משתני סביבה והגדרות API/CORS ללקוח. פרסום יתבצע רק במסגרת הרשאת הסטודנטית והגישה הזמינה לחשבונות.

בדיקות: הרצת כלל הבדיקות הרלוונטיות, אימות של לפחות שתי migrations, שחזור ההקמה מול מסד נקי ללא עריכות ידניות במסד, בדיקת תוכן Git לאיתור סודות ותוצרים ובדיקות פעולה להזדהות ולהזמנה בשירותים שנפרסו. יש להבחין בין התנהגות שנבדקה מקומית לבין פריסה שנחסמה עקב חוסר גישה.

## 5. מצב נוכחי ושער האישור הבא

שלבים 1–4 הושלמו. שלב 5 אושר והושלם: מומשו הרשמה, גיבוב סיסמאות, התחברות, JWT חתום, claims של User/Admin, נתיבים מוגנים וחשבונות הדגמה ייעודיים. בדיקות יחידה ובדיקות API/PostgreSQL אמיתיות מכסות התחברות תקינה ושגויה, ולידציה, הרשמה כפולה, tokens שגויים ושפג תוקפם, 401,‏ 403 והרשאות תפקידים. CRUD לקונצרטים, endpoints להזמנה ותשלום טרם מומשו. מצב הפרסום ב־GitHub מתועד בנפרד בדוח השלב.

תידרש המתנה לאישור הסטודנטית לפני שלב 6. בסיום כל שלב שרת בהמשך יוצגו השינויים, תוצאות הבדיקות והמגבלות, ותתבקש הסכמת הסטודנטית לשלב הבא.
